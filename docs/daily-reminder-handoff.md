# 每日練習提醒交接

**狀態：尚未實作，僅完成可行性確認（2026-09-10）。**
目前 `pubspec.yaml` 沒有任何通知相依（只有 `sqflite`、`path`、`url_launcher`），
`lib/` 與 `ios/Runner/` 也沒有任何通知相關程式。

## 結論：可行，而且不需要伺服器

要的是**本地通知（local notification）**，不是推播（push）。

| | 推播通知 | **本地通知** |
| --- | --- | --- |
| 誰發出 | 伺服器 → APNs → 裝置 | **裝置自己**，app 排程後由系統觸發 |
| 需要後端 | 要 | **不用** |
| app 沒開時 | 會收到 | **會收到** |

iOS 底層用 `UNCalendarNotificationTrigger`（`dateMatching` 指定時分、`repeats: true`），
排一次就會每天固定時間重複，**不需要 app 在背景執行**——
iOS 本來就不允許可靠的每日背景執行，但本地通知由系統代為觸發，不吃這條路。

Flutter 端需要新增兩個套件：`flutter_local_notifications` ＋ `timezone`
（後者是 `zonedSchedule` 所需，用來正確處理當地時間與日光節約時間）。
iOS 還要在 `AppDelegate` 設定 `UNUserNotificationCenterDelegate`。

## 實作時會踩到的五個點

1. **通知不知道「今天已經練過了」。** 排定的本地通知到時間一定發，不管使用者做了什麼。
   標準解法是反過來取消——使用者完成每日五題時，取消今天那則、改排明天的。
   `lib/services/daily_mission.dart` 已在追蹤當日進度，掛在那裡即可。
2. **iOS 每個 app 最多 64 則待發通知。** 單一「每天重複」的通知只算 1 則，綽綽有餘；
   但若要讓每天文案不同而排成 N 則獨立通知，就必須守住這個上限。
3. **必須先取得授權。** iOS 只會跳一次系統對話框，被拒絕後就完全不會發，
   而且要使用者自己進設定開回來。時機點要挑，不要一開 app 就跳。
4. **多學習者是裝置層級的限制。** 通知綁裝置不綁學習者，
   Allen 和 Mia 共用一台 iPad 時只能發一則「該練習了」，無法分別提醒。文案要據此設計。
5. **App Store 審查指南 4.5.4**：推播不得成為 app 運作的必要條件、不得未經同意用於廣告。
   單純的學習提醒沒有問題（Duolingo 一類皆如此）。

## 與變現設計的關係

依 `docs/plans/2026-09-10-freemium-monetization-design.md`，廣告只放底部 banner，
**廣告收入完全取決於使用者是否每天打開 app**。每日提醒是提升留存最直接、成本最低的手段。

**建議放在免費層**，不要當付費特典——付費賣的是詳解、去廣告、紙娃娃全套與 5 個角色；
讓免費使用者持續回訪才有廣告收入，把提醒鎖起來等於自己掐掉留存。

## 動工前要先釐清的決策

這是新功能且改變行為，動工前應先跑 brainstorming 把以下問題問清楚，再照 TDD 實作：

- 提醒時間固定還是讓使用者自訂？預設幾點？
- 誰能開關？（設定頁的哪一層；小孩自己關得掉嗎）
- 多學習者共用一台裝置時，文案怎麼寫才不會只點名其中一個
- 完成當日任務後要不要立刻取消當天的提醒（見上面第 1 點）
- 連續未使用時要不要停止提醒，避免變成騷擾
